# REQ-0028 附件条只列正文未引用的附件

- **ID**：REQ-0028
- **类型**：`feature`
- **场景叙述**：用户打开一封正文以 `cid:` 引用多张内联图的 HTML 邮件（周报、海报、系统截图），**附件条只显示真正需要另存/打开的文件**；已经被正文渲染的内联图不再以 `image003.png` 之类的条目挤满附件条。用户仍能在正文里看到这些图片；真实附件（xlsx、wmz 等）原样保留、可打开/另存。
- **价值**：本机样本有 57 个附件，其中 55 个是正文内联图，附件条被压缩成一排回形针并裁掉，真实附件找不到；不修则「附件条」在常见周报上不可用，用户误以为客户端把附件弄丢了。
- **非目标**：
  - 不改内联图的识别/下载/`data:` 改写与渲染；正文里该显示的图片照常显示。
  - 不删除附件数据、不改 `attachments` schema、不改 `ReadScene.attachments`/`downloadAttachment` 的全量语义；只在展示投影里过滤。
  - 不做附件条的横向滚动/折叠/“+N”菜单/搜索；真实附件很多时的条带溢出不在本批。
  - 不提供“从附件条保存内联图”的新入口；该诉求另行评估。
  - 不处理歧义/未命中的情况：宁可保留，不误删。
- **约束**：
  - **只按正文实际引用过滤**：复用 `InlineImageHTML.matches` 的唯一匹配规则（先 `contentID`，再 `displayName`/去扩展名回退）；歧义（0 或 >1 候选）不隐藏。
  - **展示投影**：`MailboxViewModel.attachments` 从“全量”改为“附件条展示集”；内联渲染仍由 `ReadScene` 自己取全量附件，不依赖该投影。
  - **无网络/无 schema**：过滤是纯函数 + 内存过滤；不触网、不读写库、不加依赖/target。
  - **时序**：正文 HTML 确定后过滤（缓存正文同步命中；补拉成功后再过滤）；预览 HTML（纯文本）没有 `cid:`，不过滤。
  - **取代既有确认**：本卡取代 2026-11-21 人工确认的「内联附件继续列在附件条」（`REQ-0025` 澄清③）；决策记录 `history/decisions/2026-11-23-table-adapt-inline-attachment-filter.md`。
- **影响场景**：
  - **新建 `SCN-0022`（`mail/read/attachment-strip-inline-filter`）**：认领「内联图不进附件条 + 真实附件保留 + 无 cid 不过滤 + 歧义不误删」的 3 正 1 反。
  - 回归（不新增断言）：`SCN-0019`（内联图仍渲染）、`SCN-0020`（附件取用）、`SCN-0005`（附件下载）。
- **澄清记录**：
  - 2026-11-23 **人工确认**：附件条隐藏正文内联图（用户选择「表格 + 附件条隐藏内联图」方案）；接受「内联图不再从附件条另存」的代价；不做附件条横向滚动。
  - 2026-11-23 默认（未经人工）：过滤在正文 HTML 到达时同步执行，不做「渲染成功后才隐藏」，避免一次 57 个回形针的闪动；渲染失败时对应附件仍不显示，记残余风险。
- **状态**：`accepted`（2026-11-23 方案确认；实现/验证完成后转 `delivered`）
- **验收归属**：`SCN-0022` 的 3 正 1 反通过 + 上述回归不退化 + 约束逐条无违反；需求不另立测试。
