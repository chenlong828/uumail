# REQ-0044 草稿箱与服务器 Drafts 文件夹双向合并同步

- **ID**：REQ-0044
- **类型**：`feature`
- **场景叙述**：草稿箱不再只是本机列表：打开草稿箱时先显示本地草稿，随后在后台与服务器 Drafts 文件夹对账。本机新写/改过/删掉/发出的草稿会推到服务器；服务器上新增、修改或删除的草稿会合到本地。两边都改过的同一封草稿按合并策略**两份都保留**：原行收下服务器版本，本地改动另存为一份新草稿并在同一轮同步里上传成服务器上的第二份，由人决定删哪一份。同步失败（离线/被拒）不阻塞本地读写，草稿仍是本地权威，下次进入草稿箱或保存/删除后自动重试。
- **价值**：不做的后果——草稿只在本机，换一台设备或在 OWA 里写的草稿看不见；在手机/网页继续写同一封草稿时两边各写各的，合并只能靠人猜。双向同步让「任意端写、任意端接着写」成立，而合并策略保证任何一端都不会被另一端悄悄覆盖。
- **非目标**：
  - 不做草稿附件与内联图同步（附件随草稿上传/下载不在本期）。
  - 不做 Bcc、草稿已读状态、服务器草稿的「发送中」标记。
  - 不做后台定时轮询：同步触发点是进入草稿箱、保存、删除、发送与手动刷新。
  - 不改 Message/文件夹同步、不改收件箱/发件箱路径、不改发送入队与 Outbox 状态机。
  - 不新增 target；不改搜索；不把服务器草稿写进 `messages` 表（草稿只进本地草稿行）。
- **约束**：
  - 协议：EAS 16.1 的 `Sync` 命令在 Drafts 文件夹上 `Add`/`Change`/`Delete`（MS-ASEMAIL §4.4）；我们客户端已用 `16.1`。草稿文件夹按 `Folder.type == 3` 识别。
  - 本地草稿仍是 `outbox` 的 `state='draft'` 行；v13 增加 `server_id`、`draft_hash` 与 `draft_tombstones` 表。
  - 内容指纹 = 收件人/抄送/主题/正文（HTML 优先）拼接串，存 `draft_hash`；`draft_hash != 当前指纹` 判定「本地改过」，服务器指纹不同判定「服务器改过」。
  - 同步顺序固定：先拉后推。拉：新增/修改按指纹合并（两边都改 → 复制本地版本再采用服务器版本）；服务器删除且本地未改 → 删本地行，本地改过 → 解绑保留本地（下轮重新上传）。
  - 推：未绑定行 `Sync Add`（ClientId = 本地行 id）→ 绑定 ServerId；已绑定且本地改过 → `Sync Change`；tombstone → `Sync Delete`。
  - 发送已绑定草稿、删除已绑定草稿，都在同一事务里落 tombstone；即使离线，下一次草稿同步会把服务器副本删掉。
  - 同步单飞（同一时刻只跑一轮）；失败只返回错误，本地草稿不受影响。
  - 网关实测（2026-11-27）：① 草稿写命令返回的 SyncKey 会被下一次 `Sync` 以 status 3/4 拒绝，写后必须重新 `SyncKey=0` 引导取新 key；② Drafts 文件夹**为空**时窗口 `Sync` 也返回 status 3/4（收件箱/已发送正常），草稿同步把这种情况当作「服务器没有草稿」，取新 key 后继续推送本地草稿。
- **影响场景**：
  - `SCN-0031`（`mail/send/drafts`）：新增 `T-SCN-0031-05`（拉取绑定、上传绑定、冲突保留两份、删除/发送 tombstone），场景做增量重验。
  - 回归（不新增断言）：`SCN-0006`（发送入队不变）、`SCN-0016`（sheet 撰写不变）、`SCN-0028`（草稿箱仍是第四段）。
