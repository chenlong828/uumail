# REQ-0026 附件取用交互（双击打开、右键另存为）

- **ID**：REQ-0026
- **类型**：feature
- **场景叙述**：用户在阅读页附件条看到附件后，**双击**某个非内联附件：本地缓存已有则直接打开；没有则自动下载到本地缓存（同一附件只下载一次，缓存满按既有 2 GB 最旧优先清理）并用系统默认程序打开。用户也可**右键**（含 Control-单击）附件，从系统菜单中选择「打开」或「另存为…」；另存为把副本保存到用户选择的位置，缓存文件保留。**单击不触发下载或打开**（只选中）。正文中以 `cid:` 引用的内联图片仍按 `SCN-0019` 在打开邮件时自动取用并显示——这是既有能力，本卡只回归，不重新认领。
- **价值**：不做则工作邮件里的 PDF、发票、行程单只能单击后被动打开，不能另存到用户指定位置；误点即下载/打开，没有标准 macOS 的「双击打开、右键更多」选择；缓存复用与容量策略对用户不可见，反复下载或磁盘失控会直接影响日常取件。
- **现状（供设计定位；本卡不下根因结论）**：
  - 附件条是 SwiftUI `Button`，**单击**即 `onOpenAttachment` → `MailboxViewModel.download` → `ReadScene.downloadAttachment`（缓存命中/单飞下载/落盘/`markAttachmentCached`）→ `NSWorkspace.shared.open(url)`。**没有双击手势、没有右键菜单、没有另存为**（`Sources/uumail/MessageBodyView.swift:125-145`、`Sources/uumail/MailboxView.swift:87-90`、`Sources/Presentation/MailboxViewModel.swift:305-311`）。
  - 缓存命中直接返回、不触网；未命中按 `fileReference` 单飞整包下载；`FileAttachmentFiles` 每次写入后按总上限 2 GB、修改时间最旧优先删除（`Sources/Scenes/ReadScene.swift:173-202`、`Sources/Composition/Platform/FileAttachmentFiles.swift:5-77`）。现有 `FileAttachmentFilesTests` 3 例覆盖存入/命中、最旧优先、未超限不删。
  - `download(_:)` 用 `try?` 吞掉错误，视图只判断 `url` 是否为空；**没有用户可见的下载失败提示**（`Sources/Presentation/MailboxViewModel.swift:307-311`）。
  - 内联图片自动下载/显示已由 `REQ-0025`/`SCN-0019` 交付（L1+L2 verified；`ReadScene.renderInlineImages`、`MailboxViewModel.inlineImageHTML`）；`SCN-0019` 的 A5 真实样本冒烟仍未执行，是发布前/人工项。
  - 用户截图 1 是「附件条两个 `imageNNN.png` + 正文空白」的内联图片形态（与 `SCN-0019` 的样本 B 同形）；截图 2 是「附件条三个 PDF + 正文有内容」的普通附件形态。截图只作形态证据，真实主题/发件人/地址/编号不入库。
- **非目标**：
  - 不做附件编辑、内置预览器、云端预览、图库、批量下载、拖拽导出、分享菜单。来源：用户未提 + 假设（未经人工，D6）。
  - 不做 25MB 上限判断、断点续传、`AttachmentName` 回退；这些是 `SCN-0005` 的既有欠账，本卡不替它补。来源：既有场景欠账 + 用户未提。
  - 不改内联图片的识别/改写/CSP/远程开关；不做 `srcset`、CSS 背景图、VML 内联图片。来源：`SCN-0019` 已验证边界。
  - **不改缓存算法**：沿用 2 GB、修改时间最旧优先；不把用户口语里的「LRU」升级成按最近访问时间淘汰。来源：用户「按之前设计」+ `history/decisions/2026-11-09-attachment-cache-cap.md`。若要做真正 access-based LRU，属既有决策变更，另行确认。
  - 不改 `attachments` schema、`MailDomain.Attachment`/`AttachmentFiles` 公开契约、EAS 命令形状。来源：推导（现有字段与端口足够）。
  - 不做右键菜单的脚本/服务/分享扩展，不新增第三方依赖或 target。来源：项目约定。
  - 不把用户截图里的附件名、数量、邮件主题/发件人/编号写成硬契约。来源：`auto-confirm` §2。
- **约束**：
  - **双击才触发下载/打开**：单击不得触发下载或打开（可只选中）；双击缓存未命中时发起一次下载，命中时 0 网关请求。来源：用户原话 + 假设（未经人工，D2）。
  - **自动下载进既有缓存**：与既有附件缓存同一目录、同一 `fileReference` 键；下载完成后再打开；不得绕过 `AttachmentFiles` 另起缓存。来源：用户「放入缓存区」+ 现有 `downloadAttachment` 接线。
  - **已下载不重复下载**：缓存命中直接打开；同一附件并发双击共享一次下载（既有 `FlightBoard` 单飞）。来源：用户原话 + 现有单飞。
  - **缓存满按既有设计清理**：总上限 2 GB，按修改时间最旧优先；只删缓存文件，**不删邮件、正文、附件元数据**；被清理后再次打开可重新下载。来源：用户「按之前设计」+ 2026-11-09 决策。用户原话「邮件……被清理」按上下文理解为缓存文件；若本意是清理邮件本身，属重大范围冲突，需另行确认，本卡不按该解读执行。
  - **用系统默认程序打开**：双击与右键「打开」等效，走 macOS 默认打开方式；不在 app 内预览。来源：用户「使用 Finder 的程序打开」+ 现有 `NSWorkspace`。
  - **右键菜单至少含「打开」「另存为…」**：右键/Control-单击出现系统菜单；「打开」与双击等效；「另存为…」让用户选择目标位置并把副本写入，缓存文件保留；取消不报错、不改缓存。来源：用户原话（「等」是示例，不把菜单项数量写成契约）。
  - **失败可见**：下载失败不得打开不存在的文件，给用户可见提示并可重试；另存为写入失败给提示；缓存文件被外部删除时按未命中重新下载，不打开缺失文件。来源：推导（现有 `try?` 吞错）+ 可用性。
  - **不回归**：内联图片自动下载/显示（`SCN-0019`）、远程开关/CSP（`SCN-0013`/`SCN-0018`）、正文阅读（`SCN-0004`）、字号（`SCN-0015`）、白底（`SCN-0010`）不退化。来源：既有已验证/已设计承诺。**A8 的 `SCN-0019` 回归口径（2026-11-20 第 2 轮）**：指其自身 `T-SCN-0019-01..04`（内联图片自动取用/渲染/失败降级），不含其边界段引用的旧「附件条点击=下载/打开」口径；后者由本卡 D2/A7 取代，见设计裁定。
  - **真实数据脱敏**：真实邮件/附件只做冒烟；自动化夹具用假附件名与假字节，不写真实主题、发件人、地址、账号、路径。来源：`af-flow-rule` §5。
  - **预算**：不新增 target/第三方依赖；单文件 ≤300 行（项目架构门）。来源：`AGENTS.md`/架构门。
  - **契约变更需确认**：若实现确需改 `attachments` schema、`Attachment`/`AttachmentFiles` 公开契约或 EAS 命令，按 `auto-confirm` §3 提人工确认；本卡不默认批准。来源：`auto-confirm` §3.1。
- **影响场景**：
  - **`SCN-0005`（`mail/read/attachment-download`，`designed`）**：建议在原场景上增量（双击/右键/另存为/单飞/缓存/失败），因为它的结果就是「附件下载与打开」，且尚未 `verified`，不是历史承诺；设计需补新断言并重验。若设计选择新建场景，须说明为何不把同一结果拆成两个场景，并避免与 `SCN-0005` 重复认领。**设计裁定（2026-11-20）**：新建 `SCN-0020`，不增量 `SCN-0005`；理由见下。
  - `SCN-0019`（`verified`）：只回归内联图片自动下载/显示与缓存复用，不改其断言；A5 真实样本冒烟为发布前/人工项。
  - `SCN-0013`/`SCN-0018`/`SCN-0004`/`SCN-0015`/`SCN-0010`：只回归，不新增断言。
  - 需求不另立测试；验收 = `SCN-0020` 3 正 1 反通过 + 上述回归不退化 + 约束逐条无违反。
